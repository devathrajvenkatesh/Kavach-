# KAVACH – Expected Outputs for Email and PDF Scanning

## 1. Purpose

This document outlines the expected outputs generated by KAVACH – AI-Powered Cybersecurity Intelligence and Defence System (*The Possessed Butler*) when users upload email (`.eml`) and PDF (`.pdf`) documents.

KAVACH is designed to execute two primary concurrent tasks:
1. **Document Intelligence:** Comprehend, extract, and summarize uploaded document content using LLM-driven intelligence.
2. **Security Intelligence & Control:** Detect malicious prompt injection directives, isolate untrusted content, and enforce strict action authorization using modular defense layers.

---

## 2. Expected Output Structure

For every scanned email or document, the system interface is expected to surface three structured panels:

### A. Document Intelligence
- **File Name:** Identifies the uploaded document.
- **File Type:** Format classification (`Email / RFC 5322 MIME` or `PDF Document`).
- **Content Summary:** High-utility, factual synopsis of legitimate operational content.
- **Important Information Extracted:** Key parameters (dates, items, quantities, points of contact).
- **Suggested Next Steps:** Recommended follow-up actions for user consideration.

### B. Security Intelligence
- **Classification:** `BENIGN` or `MALICIOUS`.
- **Risk Level:** `LOW`, `MEDIUM`, or `HIGH`.
- **Attack Type:** Detected adversarial vector (e.g., Direct Prompt Injection, Instruction Hijacking, Roleplay Attack, Encoded Attack, Indirect Injection).
- **Suspicious Instruction Details:** Specific trigger patterns, signatures, or payload strings detected.
- **Detection Status:** Status of security layer identification (`Detected`, `None Detected`).

### C. Action Control
- **Proposed Action:** Operation requested either by user or embedded context (e.g., `READ`, `SUMMARIZE`, `WRITE_FILE`, `SEND_EMAIL`).
- **Permission Decision:** `ALLOWED`, `DENIED`, or `APPROVAL REQUIRED`.
- **Execution Status:** Indicates whether the action was executed, denied, or held for confirmation.
- **Reason:** Deterministic rationale explaining policy enforcement or mitigation.

> *Note:* An action must never be reported as blocked unless the security system independently verifies that the unsafe operation was actively prevented from executing.

## 6. Responsibilities of Each Component

```
User Task Submission
         │
         ▼
[ LLM / AI Butler ]  ◄── (Extracts context, identifies user intent)
         │
         ▼
[ Security Detector ] ◄── (Identifies injection heuristics, Base64 analysis)
         │
         ▼
[ Content Guard ]     ◄── (Quarantines external directives, preserves valid facts)
         │
         ▼
[ Permission Manager ]◄── (Validates proposed actions, checks destinations/secrets)
         │
         ▼
[ Backend Engine ]    ◄── (Executes authorized actions, writes audit log)
```

### LLM / AI Butler
- Understand and parse user-submitted tasks.
- Read and synthesize email and PDF content.
- Extract legitimate operational details (dates, tasks, action items).
- Propose necessary subsequent actions without executing them directly.

### Security Detector
- Identify explicit system override attempts and debug invocations.
- Detect message boundary tampering and delimiter injection.
- Detect adversarial roleplay framing and persona coercion.
- Scan and safely decode obfuscated inputs (Base64/Hex).
- Calculate confidence scores and assign risk levels (`LOW`, `MEDIUM`, `HIGH`).

### Content Guard
- Enforce strict separation between trusted user prompts and untrusted external data.
- Isolate external data within explicit delimiters (`<untrusted_content>`).
- Excise and defang command blocks while preserving valid business context.
- Prevent external data from elevating its privilege or impersonating system prompts.

### Permission Manager
- Check every proposed action against deterministic security policies.
- Deny dangerous operations (`leak.txt`, credential exposure, unauthorized external emails).
- Hold sensitive legitimate actions (outbound messaging, file writes) for human approval.
- Maintain tamper-evident audit trails of all authorization queries.

### Backend
- Orchestrate request lifecycles across detector, guard, butler, and permission layers.
- Enforce authorization strictly before invoking physical I/O or services.
- Record comprehensive audit logs and serve dashboard results via REST API endpoints.

## 7. Important Security Requirements

1. **Secret & Credential Isolation:** Never expose or write live API keys, master credentials, or canary tokens under any condition.
2. **Simulation Only:** Never execute arbitrary commands or instructions sourced from untrusted documents.
3. **No File Leakage:** Never create or populate `leak.txt` during test execution or benchmarking.
4. **Context Preservation:** Do not reject an entire document solely because an injection attempt is detected; sanitize the hostile block and preserve legitimate operational details.
5. **Fail-Closed Permissions:** Deny sensitive actions by default if policy evaluation is inconclusive or if untrusted content attempts self-authorization.
6. **Separation of Detection vs. Blocking:** Distinguish between merely detecting an attack and confirming that the unsafe action was prevented.
7. **Explicit Unverified Tagging:** Mark outcomes as `UNVERIFIED` if runtime execution logs lack sufficient proof of prevention.
